# Local Network Radar

SwiftUI MVP для iPhone и iPad: поиск доступных устройств в локальной IPv4-сети, имена Bonjour, ручные метки доверия и предупреждение о новых неизвестных адресах после завершения поиска.

Требования: iOS/iPadOS 17.0+, Xcode 16 или новее. Сторонних зависимостей нет.

## Запуск в Xcode

1. Откройте `LocalNetworkRadar.xcodeproj` и выберите схему `LocalNetworkRadar`.
2. В target приложения → Signing & Capabilities выберите свою Team и задайте свой Bundle Identifier, если стандартный занят.
3. Выберите физический iPhone, подключённый к Wi-Fi, и нажмите Run.
4. Нажмите «Сканировать» и разрешите доступ к локальной сети.
5. Откройте найденное устройство и нажмите «Это моё устройство». Действие также доступно свайпом в строке.

Права multicast, Network Extension, доступ к SSID и App Groups не используются. Не добавляйте multicast entitlement без выданного Apple разрешения.

## Сборка без своего Mac

В комплекте `.github/workflows/build-ios.yml`: ручная сборка на macOS-раннере GitHub Actions.

1. Поместите содержимое этой папки в корень своего GitHub-репозитория. Сохраните каталог `.github`.
2. Откройте Actions → Build iOS app → Run workflow.
3. Workflow запускает XCTest в симуляторе, затем собирает приложение для физического устройства.
4. После успешного запуска скачайте артефакт `LocalNetworkRadar-unsigned-IPA`. Внутри лежит `LocalNetworkRadar-unsigned.ipa`.

IPA не подписан. Для установки его нужно подписать выбранным вами способом. Проект не продлевает срок действия подписи. Доступность и стоимость macOS-раннеров зависят от условий вашего аккаунта GitHub. Сам workflow из этой среды не запускался.

## Как работает поиск

Сначала `NWPathMonitor` возвращает реальные типы и имена интерфейсов. Из них выбирается Wi-Fi либо Ethernet с IPv4-адресом. `getifaddrs` читает адрес и фактическую маску. Если одновременно доступны Wi-Fi и Ethernet, приоритет у Wi-Fi. Cellular, loopback и VPN-интерфейсы не выбираются. Каждое соединение привязано через `requiredInterface` к выбранному интерфейсу.

Перед массовым сканированием короткоживущие `NWListener` и `NWBrowser` объявляют и находят собственный уникальный сервис `_lnradar._tcp`. Это служебный тип, отдельно внесённый в `NSBonjourServices`. До окончания проверки TCP-пул не запускается: пользователь успевает ответить на системный запрос. `.ready` браузера не используется как доказательство предоставленного доступа. Ошибка DNS PolicyDenied показывает экран настройки доступа; таймаут проверки показывается как неопределённая ошибка, а не как доказанный отказ.

Затем параллельно работают TCP-проверка и Bonjour. Максимум 16 адресов × 5 портов = 80 TCP-соединений. Для каждого порта действует таймаут 0,8 секунды. Проверяются только `80`, `443`, `22`, `445`, `62078`. На 443 проверяется TCP, TLS-рукопожатие не выполняется. При `.ready` порт добавляется в `openPorts`, соединение сразу закрывается. HTTP-запросы и другой прикладной трафик не отправляются. Отказ в соединении и таймаут не помечаются как открытый порт.

Bonjour ищет фиксированные типы `_http._tcp`, `_https._tcp`, `_ssh._tcp`, `_airplay._tcp`, `_raop._tcp`, `_hap._tcp`, `_ipp._tcp`, `_printer._tcp`, `_smb._tcp`, `_googlecast._tcp`. Wildcard `_services._dns-sd._udp` не используется. `NWBrowser.Result.endpoint` содержит адрес сервиса, а не готовый IP. Поэтому `DNSServiceResolve` получает hostname, а `DNSServiceGetAddrInfo` получает IPv4-адреса на том же интерфейсе. Разрешаются максимум 8 сервисов одновременно, с таймаутом 3 секунды на сервис.

Устройство из Bonjour добавляется даже без доступного TCP-порта из списка. Объявленный Bonjour-порт не считается открытым без успешной TCP-проверки. Результаты объединяются по IP. `friendlyName` содержит пользовательское имя сервиса, `hostname` содержит имя DNS: это разные поля. Сам iPhone и адреса вне выбранной подсети отбрасываются.

На маленькой подсети Bonjour работает не менее 6 секунд. На обычной /24 нижняя оценка при сплошных таймаутах составляет около 13 секунд плюс проверка разрешения и накладные расходы; это не обещание времени на любом Wi-Fi. Смена адреса или маски во время поиска приводит к сбросу результатов. При отмене закрываются TCP-соединения, браузеры, DNS-SD-запросы и временный listener.

## Ограничения, которые нельзя скрывать

- Это список обнаруженных сервисов и доступных адресов, а не достоверный список всех клиентов роутера. Закрытые порты, спящий режим, изоляция клиентов, фильтрация и подавление mDNS дают пропуски. Пустой результат не доказывает, что в сети нет устройств.
- В MVP поддерживается IPv4 на одном физическом интерфейсе за запуск. IPv6-only сети и соседние подсети не сканируются. Для подсетей более 1024 других адресов поиск не запускается, а интерфейс сообщает реальную маску и лимит. Подмена маски на /24 не выполняется.
- Метки доверия хранятся по CIDR и IP. При смене DHCP-аренды другой хост может получить доверенную метку. Разные Wi-Fi с одинаковыми CIDR и IP не различаются. Это ручная пометка для списка, не криптографическая идентификация. Для устойчивой идентификации нужен дополнительный источник, например согласованная интеграция с роутером.
- MAC-адреса и ARP-таблица не читаются. OUI и производитель не выдумываются. Значки приблизительны: наличие 62078 не доказывает, что это iPhone, а наличие HTTP не доказывает, что это роутер.
- Здесь не используется ICMP. Утверждение исходного промпта о полном запрете любого ICMP на iOS слишком категорично: у Apple есть пример SimplePing. Выбор TCP в этом MVP является решением реализации, а не выводом о невозможности ICMP вообще.
- Предупреждение появляется в приложении после полного поиска, если обнаружены новые IP без метки доверия. Первый поиск считает новыми все неизвестные адреса. Сравнение идёт с предыдущим полным результатом для того же CIDR в текущем сеансе приложения; после перезапуска эта история сбрасывается. Отменённый поиск её не обновляет.
- Постоянного фонового мониторинга и push-уведомлений нет. Уход в фон прекращает поиск; показ системного диалога разрешения не должен его отменять. «Неизвестное» не означает «злоумышленник».
- Пять портов и ограниченный параллелизм не гарантируют прохождение App Review.

## Проверки

В этой среде нет macOS, Xcode и iOS SDK. Здесь не выполнялись сборка iOS, XCTest, подписание или запуск на iPhone. Статические проверки структуры проекта и Swift-синтаксиса описаны в `VALIDATION.md`. Настоящая проверка компиляции выполняется через Xcode или включённый workflow.

В Xcode: Product → Test. Либо на Mac:

```bash
xcodebuild -project LocalNetworkRadar.xcodeproj \
  -scheme LocalNetworkRadar -configuration Debug \
  -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO build-for-testing
```

Для выполнения тестов выберите конкретный установленный iPhone-симулятор в Xcode. Сетевые разрешения и обнаружение проверьте отдельно на физическом iPhone:

1. Первый запрос: разрешить доступ, дождаться поиска.
2. Отказать в доступе: увидеть объяснение и рабочий переход в Настройки; включить доступ и повторить.
3. Запустить на компьютере в той же сети `python3 -m http.server 80` с нужными правами: увидеть TCP 80. При невозможности открыть 80 используйте сервис на одном из остальных проверяемых портов.
4. На Mac объявить отдельный Bonjour-сервис, например `dns-sd -R "Radar Test" _http._tcp local. 8080`: увидеть имя, но не добавлять 8080 к проверенным открытым портам.
5. Пометить устройство доверенным, перезапустить приложение, выполнить новый поиск. Метка должна сохраниться.
6. Остановить поиск и свернуть приложение во время другого поиска: он должен прекратиться без предупреждения о новых устройствах.
7. Проверить реальную /23 или /22, отсутствие Wi-Fi, смену Wi-Fi, устройство без Bonjour и со всеми пятью закрытыми портами. Последнее устройство может не появиться, и это ожидаемый предел метода.
